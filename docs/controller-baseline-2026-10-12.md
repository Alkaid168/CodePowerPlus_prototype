## 4. 项目定位与技术解释

教练提出的功能可串成“题目考点 → 做题证据 → 能力画像 → 推荐/提示”。
学校 OJ 提供评测，码力加加消费题面与评测记录；手工、文件导入或将来获准的接口都可以作为输入，不需要先拿到 OJ 源码。

| 技术 | 通俗职责 | 当前边界 |
| --- | --- | --- |
| FastAPI / Python | 接待网页请求、执行分析与审核等规则 | 已有本地服务代码 |
| SQLite | 保存题目、分析、审核和提交的账本 | 本地单用户原型 |
| HTML / CSS / JavaScript | 用户操作的网页工作台 | 原生模块，无前端构建步骤 |
| DeepSeek API | 给标签、评分和辅导建议的模型顾问 | 输出需要校验与人工核对 |
| Docker | 把程序与运行依赖打包便于部署 | 已有配置，本轮未构建验证 |
| Nginx | 公网部署时的入口和转发层 | 当前本地阶段未引入 |

当前“知识体系”是三级题目标签词表，不能把分类父子关系称为学习前置关系。
现有学习路径只是层级路径；画像采用独立题目结果规则，推荐按薄弱度与难度匹配，尚非校准后的知识追踪与教学规划模型。

## 5. 后续建议（未新增开发授权）

1. 先完成中断的题面公式修复，保留题目含义、样例和分析审计历史，并恢复完整测试及浏览器验收。
2. 人工复核已有题目，随后用学校题目建立独立标签与难度参考；先统一“该标哪些标签”的准则，再评价模型。
3. 能力画像阶段解决实际解法证据：用树状数组通过不自动证明线段树掌握。题目的多解法标签继续保留，学生能力证据另行设计。
4. 在可运行基线上确定一个主要研究问题，开展模型/提示词或能力模型的对比，再评估推荐、辅导和真实用户反馈。
5. 确认中期日期、团队分工和可获取数据，重排立项书时间表；由总控解释设计、汇总证据、协调模块成果。

工程验证回答“系统能否正常工作”；研究实验回答“某种方法是否比基线更有效”。目前已有前者的一部分基础，后者仍需真实数据与受控比较。
