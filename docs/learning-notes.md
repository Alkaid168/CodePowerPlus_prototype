# 项目开发学习笔记

这些说明面向项目负责人：你负责判断方向和检查效果，代码由代理实现。理解关键边界比记住每一行语法重要。

## 教练为什么说不需要 OJ 源码

OJ 是裁判，输入代码，输出 AC、WA、TLE 等结果。码力加加是旁边的学习教练，读取题目和判题记录，回答“练了哪些知识、哪里可能不熟、下一步练什么”。只要双方能交换题目和记录，就能协同，不需要先重写或拿到裁判的内部实现。开发初期通过手工导入交换数据；未来 OJ 的 API 或导出文件是另一种输入渠道。

## 知识树：它就是题目标签词表

“数学 → 数论 → 素数”是一条分类链，像图书馆的书架目录。它回答的唯一问题是“这道题考什么”，所以节点只有名字和层级：没有难度、讲解、典型算法、学习目标，也没有先修关系。你看不到“编译与调试”“C++ 现代特性”这类节点，不是因为它们不重要，而是因为没有一道题的标签会是它们。

L1 是领域（数学、图论……），只用于聚合统计；L2 既可以是分支（数论），也可以是知识点本身（数学 → 快速幂）；L3 是更细的知识点（数论 → 素数）。先修顺序属于教学环节，由题目证据和树的层级近似表达，不单独维护第二套结构，避免两份数据互相打架。

当前树存为 JSON 文件，Python 负责遍历；几百个节点的规模不需要图数据库。

## 为什么使用稳定 ID 和版本

名字像人的称呼，ID 像学号。“01 背包”将来改称“0/1 背包问题”，只改显示名，原来的题目关系仍能找到同一个知识点。`taxonomy_version` 表示当时使用的是哪一版知识目录，避免研究时把不同版本的标签混为一谈。

知识节点不带难度字段；题目难度用 Codeforces 风格的 800–3500 评分，由题目分析给出。锚点（800 签到、1200 入门/上机考试、1600 算法加思维、2000 区域赛铜牌）是人工约定的标尺，不是从真实标注回归出来的，仍需要校准实验。

## JSON Schema 与业务校验

JSON 是大家约定的表单。JSON Schema 检查“字段有没有填、类型对不对、值是否合法”；业务校验进一步检查“父节点真的存在吗、层级连不连续、标签有没有重复、有没有同时标祖先和后代”。就像报名表格式正确，并不等于填的学号真属于这个学校。两层都需要。

## 分析、审核和事务

模型分析只产生候选，人工核对理由后才变成已审核证据。纠正会保存一个新版本，旧分析不会消失，审核意见单独记录。

数据库事务像一起提交一组操作：创建题目和创建分析要么都成功，要么都撤回，不能只成功一半。审核还检查你看到的分析编号，别人先修改后，你的旧页面不能覆盖新结果。

审核人的名字目前由本机使用者填写，它是审计标识，不是登录认证。当前是本地可信单用户工具；多人公网部署前要加入身份认证与权限。

## 能力分数怎么算

第一版使用简单且可解释的证据估计：同一题的重复尝试只取最后一次非 CE 结果；独立题目数为 n，其中 AC 数为 a，分数是 `(1+a)/(2+n)`。没有做过题显示“待评估”，一次 AC 得到约 0.667，不会立刻断言百分之百掌握。证据量置信度用 `n/(n+5)` 显示，和模型对标签的置信度是不同东西。

CE 是编译错误，不能直接认定算法知识不会。WA/TLE/RE 等在这个简单基线中统一算未通过，未来可以利用代码诊断细分原因。分数目前不是经过校准的正确率，也不是正式 BKT。

父领域的统计是汇总展示，不能据此断言每个孩子都会。例如做对二分题可以给“算法基础”提供证据，却不能凭这一点认定归并排序已经掌握。

## 推荐与学习路径

推荐只用审核过的题目，排除已经 AC 的题，按知识薄弱程度（0.6）与难度适配（0.4）排序。推荐分是一套公开权重的启发式，不是模型的神秘判断。页面展示原因与分项得分，便于发现算法不合理的地方。

学习路径就是目标在知识树上的层级：领域 → 分支 → 知识点，每一层标出当前掌握度与可练的题目。它提供当前目录上的短期建议，不承诺自动生成整个学期的最优学习计划。

## FastAPI、SQLite、Docker 与 Nginx

- FastAPI：服务窗口。浏览器发来“查知识点”“保存提交”的 HTTP 请求，它把请求交给对应 Python 函数并返回 JSON。
- SQLite：项目里的本地账本文件，保存题目、分析、审核和提交。便于开发、备份和离线演示。
- Docker：把程序、依赖和启动方式装进一个可复用的箱子，在其他机器上更容易得到一致环境。数据库放在独立数据卷，换箱子时记录不会丢。
- Nginx：部署网站时的入口，可负责 HTTPS 和把请求转到 Python 服务。本机学习原型暂不需要它。

## 工程与研究如何结合

能点按钮完成流程属于工程交付；提出可检验问题、设计对照并分析结果属于研究。比如“把题目标签当作特征，能否让学生更快找到下一个该练的知识点”，可以先比较纯难度推荐与标签薄弱度推荐，再组织真实使用评估。

仓库的自编样例和模拟学习者只证明计算流程可以复现，不能证明系统提升了真实学生成绩。标签 F1 与难度 MAE 需要单独提供预测，绝不能把标准答案当作预测得到满分。真实评估还需独立标注、训练/测试划分、时间顺序和用户样本量。

## 代码是怎么组织的（0.3 版重写）

一次请求的路径是：浏览器 → `app/api/*`（解析参数）→ `app/services/*`（业务规则）→
`app/repositories.py`（读写数据）→ `app/db.py`（SQLite）。分层的意义是**规则只有一处实现**：
标签校验只在 `services/analysis.py`，审核只在 `services/review.py`，画像公式只在
`services/profile.py`。想换接口形式或换数据库，业务规则不用重写。

依赖都装在 `app/container.py` 的 `Container` 里，所以测试能给每个用例装配「临时数据库 +
关闭模型」的独立环境。这不是为了好看：旧版把连接和配置写成模块全局变量，测试只能靠改环境
变量绕过去，容易互相污染。

前端没有用 React，而是原生 ES 模块加几个小工具：`dom.js`（创建节点）、`api.js`（请求与错误）、
`store.js`（学习者与知识树缓存）、`router.js`（`#/problems/12` 这样的地址）、`components.js`
（按钮、卡片、表格）。原因很实际：项目要在没有 Node 构建链的机器上一条命令跑起来，
多一层 npm 就多一份你无法维护的复杂度。所有界面都用 `h()` 创建节点、不拼 `innerHTML`，
因此标签名、题面里的尖括号不会变成代码。
