# MV3采集器商店发布与生产化审查（2026-10-21）

> 2026-10-22更新：当前0.4.0已实现SQLite源码去重、原子配额、受限删除与备份恢复；扩展上传/导出均分批读取。下文0.2.0差距与容量值为历史审查。用户决定先完善扩展，不以学校API/SSO为前置；未来可选独立本站认证。当前实施见`collection-storage-design-2026-10-21.md`，仍未完成真人四站、正式多人服务及商店验收。

## 结论

当前 0.2.0 是可运行的开发预览，不应直接面向全校发布。最大阻塞不是商店表单，而是四站真实账号覆盖还未验收、线上服务仍标为 `local-single-user`、没有学生身份登录/令牌自助发放/数据删除与保留机制，以及源码在 SQLite 的多份 JSON 快照中重复存储。0.2.0 已补上客户端批量上传与本地断点续传。

推荐先做一个可控试点，再决定公开商店或学校组织分发。用学校固定 HTTPS 服务域名，完成登录与账号绑定、最小权限、数据说明与删除、稳健批量同步和四站真实样本验收；不把任意 HTTPS 上传目标留给学生自填。Edge Add-ons 和 Chrome Web Store 可以复用同一个 MV3 代码包，但需要各自开发者控制台、商店素材、隐私披露和审核。

## 主要风险

| 风险 | 当前证据与影响 | 上架/试点前处理 |
| --- | --- | --- |
| 扩展权限警告过宽 | `manifest.json` 声明 `https://*/*` 可选来源，以支持用户任意输入服务器；这会削弱“只访问四站和本校服务器”的信任表达，也增加审核解释成本。 | 固定学校 API origin，并从清单移除通配 HTTPS 来源；只在用户手势授权四个 OJ 和固定 API。 |
| 服务器不能多用户上线 | `health` 显示 `local-single-user`；令牌由管理员脚本离线签发，没有校内登录、身份绑定、撤销/轮换流程。 | 接入学校现有身份认证；由后端签发短时、绑定用户/平台账号/用途的导入凭据；限流并审计。 |
| 数据用途与源码敏感度 | 用户会上传本人提交源码；当前没有产品隐私页、源码保留期限、删除接口或面向学生的完整数据流披露。 | 发布隐私政策/站内说明：字段、目的、接收方、保留期限、删除/导出、访问控制和联系渠道；上传前逐平台/源码状态确认。 |
| 真实采集可靠性未验收 | 现有自动化使用合成 DOM 与合成 CF 响应；洛谷登录结构、各站账号选择器、权限和全历史边界没有真实账号端到端证据。 | 建立每站成功/受限/登录过期/结构变化/源码不可见样例；核对提交总数、首尾游标和抽样源码；结果标记可见覆盖范围。 |
| 上传请求量过大 | 0.1.0 的 `ui.js` 用 `exportBatches(...,1)`；5000 条即 5000 个串行 POST。 | **已在 0.2.0 本地端实现第一阶段修复**：每批最多25条或目标1.5 MiB，按UTF-8 JSON实际字节拆批；单条允许到服务端8MB限制；已确认批次游标和稳定batch_id存IndexedDB，失败可断点续传。仍需对接真实服务器实测请求/超时/令牌过期。 |
| SQLite 空间重复 | 服务同时保存原批次 JSON、观测 JSON 和当前提交 payload；合成 5000 条实测，元数据约 7.4 MiB、平均 2 KiB 源码约 59.6 MiB、平均 5 KiB 约 88.8 MiB。 | 源码改独立内容表/文件对象存储，以哈希去重；观测仅保留必要字段或按期限清理；做并发写入、磁盘增长和备份恢复压测。 |
| 源码访问暴露范围 | `/api/collection/submissions` 通过平台/账号范围令牌返回源码，当前令牌可在有效期内重复调用，没有分页导出审计/撤销。 | 正式认证后按本站用户再授权；代码读取默认关闭或分权；令牌可撤销、一次性/短期刷新；记录访问审计。 |
| 可见历史被误认全量 | AtCoder 默认仅遍历官网 archive 目录；动态 offset、隐藏/删除、WAF 和历史重判会影响覆盖；任务 `complete` 只是适配器可见范围结束。 | UI/导出持续标“可见范围完成”而不叫“全量”；提供采集时间、源站、适配器版本、范围和未取原因。 |
| 商店审核/账号风险 | 过宽权限、隐私披露与实际不一致、源码上传未清楚说明、远程执行代码或商品截图夸大均可能导致拒审/下架。 | 包含完整本地功能；服务端只传数据不下发可执行代码；审核说明提供测试账号/测试步骤；预备支持与申诉联系人。 |

## 当前实现与发布准备差距

- 当前扩展包版本 0.2.0，打包 ZIP 包含开发 README；无商店图标、截图、隐私政策 URL、支持页面或 reviewer 测试说明。
- 包含 `storage`、`alarms`、`scripting` 权限及四站可选域名权限；另有宽泛 HTTPS 可选权限。需固定服务 origin 后再做最小权限与商店权限说明审查。
- 测试 263 pytest、13 Node 和两项 Edge 临时 profile 合成集成通过；没有四站真实账号数据或 1000–2000 用户负载证据。
- 扩展“重新同步”当前回扫全历史；已采记录按 ID 去重但再次上传会产生新的观测批次，观测表可能增长。0.2.0 已持久化本地上传批次与断点；导入令牌仅保存在输入框/内存，不落盘，重开后需要重新输入。
- HMAC token 带过期时间但没有撤销台账/速率限制；离线签发入口只适合小规模受控试点，不是学校生产身份系统。
- 本轮无法从当前环境实时访问官方商店网页；以上官方页面链接与项目已有 2026-10-21 发布研究入口应在申请开发者账号/点击提交前重新核实，尤其是费用、账号验证、可见性和隐私表单字段。

## 分阶段生产化建议

1. **P0 发布边界**：选定校内唯一 HTTPS API 域名；移除 `https://*/*`；补产品隐私页、数据导出/删除和用户支持入口；确认商店使用的精确扩展 Origin CORS 白名单。
2. **P1 多用户认证**：复用学校 SSO/现有用户体系；绑定学生账号和 OJ 账号；短时凭证、撤销/轮换、速率限制、审计；生产服务不能再标 `local-single-user`。
3. **P1 上传与存储**：批量/按字节切块上传，持久化上传队列与幂等键；源码内容哈希寻址，减少多份 JSON；制定保留与删除策略，落实备份恢复。
4. **P1 真实验收**：四站各选本人测试账号，逐站跑登录识别、历史分页、源码、限制/中断恢复；记录截图/响应、平台范围、行数和校验结果；不声明超出实测范围。
5. **P2 商店提交**：补图标/截图/说明/隐私政策/客服入口；核对 MV3 与商店政策；准备 reviewer 复现步骤；先受控发布/隐藏链接，再扩大受众。
6. **P2 运维与容量**：在接近 1000–2000 用户峰值的隔离环境压测批次吞吐、SQLite 写锁/迁移、源码存储增长、备份恢复、限流和监控告警；满足后再面向全校开放。

本次先完成发布/生产差距审查，再按用户选择优先完善本地扩展：0.2.0 加入按条数/字节批量上传、IndexedDB上传断点、稳定幂等批次ID和数据库v1→v2保留数据迁移，并更新上传界面。0.3.0 将结果预览改为只读总数和最近50条，JSON导出以25条为一页从IndexedDB读取并逐块写文件，降低大批源码同时驻留内存的峰值；IndexedDB升级至v3并保留既有任务、记录和上传断点。没有创建商店开发者账号、提交扩展、部署服务或向真实学生开放。
