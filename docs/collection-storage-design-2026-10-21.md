# 提交采集存储设计（2026-10-21）

> 2026-10-22：用户已授权实施，下文保留10月21日方案与旧库容量作历史记录。**当前实现以[0.4.0实施记录](collection-storage-implementation-2026-10-22.md)为准**：五表SQLite schema v2、去重源码、原子120/150 MiB配额、受限删除、迁移与备份恢复均已落地；未实际迁移正式库。

## 2026-10-21历史状态

- 扩展端用浏览器 IndexedDB 保存任务、分页断点和提交记录；数据库位于用户自己的浏览器 profile，不是 SQLite，也没有按用户配置固定容量。实际可用空间取决于浏览器和设备。
- 服务端已用独立 SQLite `data/collection.db` 接收数据，与题库/学习记录数据库隔离；默认配置 secret 未设置时上传 API 关闭。
- 当前表为 `batches`、`external_submissions`、`observations`。每份源码随 JSON payload 同时进入批次、观测和最新提交记录，重扫会继续增加观测；没有用户容量上限、删除/保留流程或生产并发压测。
- 接口限制：每个源码最多 500,000 字符；HTTP 批次最多 8,000,000 字节；扩展默认按 25 条或约 1.5 MB 组批。它们是请求限制，不是每用户总配额。
- 既有合成测试按当前表结构存 5,000 条得到约 7.35 MiB（无源码）、59.57 MiB（平均每份源码 2 KiB）、88.81 MiB（平均每份源码 5 KiB）。这不是真实用户分布、服务器压力或磁盘峰值测量。

## 建议 SQLite 架构

保留一个独立采集库，单个 SQLite 文件足以支撑本机开发和先期单机试点。按 `BEGIN IMMEDIATE` 批次事务写入；服务器启用 WAL、外键、合理 busy timeout，限制并发写入，配置离线备份和定期恢复演练。SQLite 是单文件数据库，备份时应使用 SQLite backup API 或一致性快照，不能只随意复制正在写入的主文件。

| 表 | 主要字段与约束 | 用途 |
|---|---|---|
| `collection_accounts` | `user_id, platform, account_id` 唯一；绑定状态、创建时间 | 将校内用户与其四站账号隔离；绑定验证机制由认证方案决定 |
| `collection_runs` | `run_id`、用户/平台/账号、范围、适配器版本、开始/结束时间、覆盖状态、游标摘要 | 表示一次采集/同步及其覆盖边界，不保存登录凭据 |
| `submissions` | 用户/平台/账号/提交 ID 复合唯一键；题目、时间、语言、verdict、分数、耗时、内存、源码状态、`source_hash`、首次/最近发现时间 | 保存一份当前提交元数据；不把整条 JSON 当数据库记录 |
| `source_blobs` | 用户 ID、SHA-256、字节数、源码内容；`(user_id, hash)` 唯一 | 源码独立保存，同一用户重复提交相同内容只存一份；按用户隔离哈希，便于删除和配额核算 |
| `submission_observations` | run/batch、提交复合键、观测时间、必要的变化字段 | 保留审计所需的变化历史；不复制整份源码，设定保留期 |
| `import_batches` | 用户 ID、batch ID、内容摘要、导入时间、计数 | 幂等重试收据；不长期存完整批次 payload |
| `user_storage` | 用户 ID、硬配额、已用逻辑字节、更新时间 | 在同一个导入事务内增量更新并校验硬上限；触顶时整批回滚 |

源码正文首期可放 SQLite `BLOB`，好处是单库事务、备份和删除简单；文件很小或学校已有对象存储时再把正文改为按哈希命名的对象，SQLite 只存引用。配额以“用户当前唯一提交元数据 + 用户去重后的源码正文 + 少量索引/审计余量”作为逻辑计量；SQLite 文件/WAL 的物理体积另设服务器磁盘告警，不直接当单用户配额，因为删除后文件不会自动缩小且 WAL/索引会有额外开销。

## 建议初始配额

- 受控试点建议：每用户软提醒 **120 MiB**，硬上限 **150 MiB**，统计四个平台合计；这是待产品确认的初始策略，不是当前已实施限制。
- 依据：按旧表结构的合成测量，5,000 条且平均源码 5 KiB 已约 88.81 MiB；150 MiB 给常见账号留出增长空间，且源码去重和元数据规范化后实际用量预计下降，但必须实测后校准。
- 目前单条源码 500 KB 是输入校验上限，上传批次 8 MB 是 HTTP 上限；单条上限不意味着允许无界累积。超过用户配额时服务器应整批拒绝并告知当前用量/上限，客户端保留本地数据和上传断点；用户可停止采源码、导出到本地或删除服务器数据后重试，不能静默删除旧提交。
- 150 MiB × 2,000 名用户等于约 293 GiB 的理论配额总和，不能据此推断服务器会实际占满；上线前必须根据试点真实用量分布、磁盘大小、源码选择比例和备份空间决定是否采用该值。2 核 2G 的机器不能仅凭核数/内存断言可承载 2,000 人，SQLite 写入竞争、磁盘和峰值请求还需实压。

## 决策顺序

1. 先做单机 SQLite 规范化、源码去重、整批原子配额检查、用户数据删除和备份恢复测试。
2. 受控试点启用软提醒 120 MiB / 硬限制 150 MiB，记录匿名化的用量分布和峰值写等待。
3. 用试点数据校准配额、磁盘预警和源码保留期限；若并发写锁或恢复目标达不到，再评估 PostgreSQL/对象存储。
